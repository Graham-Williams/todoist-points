# CLAUDE.md — Todoist Points

Guidance for Claude Code / agents working in this repo.

## What this is

A personal gamification layer for Todoist: earn points for completed tasks (valued by hand in the **Review** tab) and for daily **habits**, spend them on rewards. Local-first, single-user (Graham). Pilot project for a PM-style autonomous coding workflow — Graham describes features in plain English, agents implement, Graham reviews the **running app** (behavior, not diffs) and merges.

## Stack

- Next.js 16 (Turbopack builds) + TypeScript + Tailwind CSS
- SQLite via `better-sqlite3` (local file, gitignored)
- Drag-and-drop reorder via `@dnd-kit/core` + `@dnd-kit/sortable` + `@dnd-kit/utilities` (touch-friendly, keyboard-accessible)
- Todoist unified API v1 (`https://api.todoist.com/api/v1`), auth via `TODOIST_API_TOKEN` env var

## Earning model (important)

Points are assigned **by hand in the app**, not by Todoist labels or priority. The Review page (`/review`) has two sections. **Upcoming** lists open Todoist tasks with a due date; points set there ahead of time are paid out automatically on completion (see "Upcoming"). Every other newly synced completion lands in **Completed** (the review queue), where Graham assigns it a point value or discards it (see "Review queue"). Labels play no part in scoring (the old label-points config page was removed; `label_points` stays in the schema, unused). The other way to earn is **Habits** (`/habits`): ticking a daily habit earns its points, and ticking every habit for a day earns a bonus (see "Habits").

## Run / test

> Keep this section updated as the project gains commands.

First-time setup:
1. `npm install`
2. `cp .env.example .env` and set `TODOIST_API_TOKEN` to your real token (`.env` is gitignored).

Commands:
- Dev server: `npm run dev` → http://localhost:3000
- Production build: `npm run build` — note the config uses `output: "standalone"`, so serve the build with `node .next/standalone/server.js` (`next start` doesn't support standalone output); in production it runs in Docker (see Deployment section)
- Lint: none — there is no `lint` script (Next.js 16 removed `next lint`; adding ESLint is issue #20). Verify with `npm test` + `npm run build`.
- Tests: `npm test` (`node --test 'src/**/*.test.ts'`, native TS type-stripping, no runner dep). Pure modules are imported directly. **Real-DB tests** import `src/test-support/hooks.ts` first (a side-effect import), then load app code with `await import(...)`: the hooks resolve `@/`, `next/server` and our extensionless relative imports, and point `DB_PATH` at a fresh temp file (deleted on exit), so route handlers and `queries.ts`/`habits.ts` run against the real schema. `node --test` gives each file its own process, hence its own DB. Todoist is stubbed by replacing `globalThis.fetch` (see `src/app/api/sync/route.test.ts`).

The SQLite DB is created automatically at `./data/todoist-points.db` on first run (schema self-initializes). Both `.env` and `data/` are gitignored — never commit them.

Both actions dispatch the global `todoist:synced` event on success so `DashboardRefresh` re-runs `getStats()` (balance + list update via the existing machinery); controls disable while a request is in flight, and errors show a subtle inline message with a Dismiss.

Client-validates an integer in [1, 100000] (Save disabled otherwise), then `PATCH /api/ledger/<id>` with `{ points }` → `updateEarningPoints(id, points)` in `queries.ts` (`UPDATE ledger SET points = ? WHERE id = ? AND type = 'earn'`). **Scope: earnings only, points only** — not the description, not redemptions. Editing touches ONLY the ledger row's `points`; it does NOT touch `processed_completions`/`source_id`/`description`/`type`/`created_at`, so sync never re-awards. The PATCH route validates `id` (positive int → 400) and `points` (integer [1,100000] → 400, matching the review-award validation style), 404s if no such earn row, 500 on error.

The route validates `id` as a positive int (400 otherwise), 404s if no such earn row, 500 on error. **Scope: earnings only** — there is deliberately no remove control on redemptions (that would be a refund, different semantics). **CRITICAL INVARIANT:** removing an earning deletes the `ledger` row ONLY and leaves `processed_completions` intact. The earning's `source_id` is the Todoist completion id, which stays in `processed_completions` from sync; the sync loop skips any completion already there (`src/app/api/sync/route.ts`: `if (alreadyProcessed.get(task.id)) continue;`), so leaving that row is exactly what prevents the removed earning from being re-awarded on the next 15s sync.
  - Both `deleteEarning` and `updateEarningPoints` guard with `... WHERE id = ? AND type = 'earn'`, so neither can ever touch a `redeem` row (a redeem id 404s). Manual-review awards are equally safe to edit/remove (they're `earn` rows, in `processed_completions` too). (This component replaced the former `RemoveEarningButton.tsx`, folding its two-step-confirm remove logic in alongside the new Edit.)
- **Editable reward cost:** the `/rewards` page supports inline editing of a reward's cost — an "Edit" button reveals a number input + Save/Cancel; client validates an integer ≥ 1, PATCHes `{ cost }`, then refetches rewards + balance (controls disabled while in flight). The PATCH route validates `cost` as a positive integer (rejects non-finite/`< 1` with a 400), consistent with add-reward validation.

### Points model (as built)
Sync is idempotent via `processed_completions` (keyed on Todoist completion id): every completion is marked processed in the same transaction that queues it, and the `alreadyProcessed` guard runs first, so re-syncing never re-queues — and a completion that was awarded, discarded, or whose earning was later removed never comes back. Earn read queries also filter `points > 0` defensively.

**Balance = `SUM(ledger.points) + SUM(balance_adjustments.delta)`**, computed ONLY by `getBalance()` in `queries.ts`. Every consumer goes through it: `getStats()` (dashboard + `/api/dashboard`, which the rewards page reads), the redeem check, and the `newBalance` in review/ledger/balance/habit responses. Don't add a second SUM anywhere. "Total earned" / "Total spent" stay lifetime ledger figures and ignore adjustments. Redeem checks `balance >= cost` and inserts the negative ledger row in one transaction.

### Sync precedence
For each completion: the `alreadyProcessed` guard runs FIRST (so re-syncing a stale window never re-awards, re-queues or re-deletes anything). Then, if `task_point_overrides` has a row for `task.id`, sync awards **exactly** that value as an `earn` row (`source_id` = completion id, description `"<content> (pre-assigned)"`, stripped to the clean title on the dashboard), **skips `pending_review`**, and deletes the override in the same transaction (an override is one-shot). Otherwise the completion is inserted (`INSERT OR IGNORE`) into `pending_review`. `markProcessed` runs for every completion. The `/api/sync` response reports `scanned`, `newlyQueued`, `preassignedAwarded` and the `pendingReview` total.

### Upcoming — points set ahead of time (`task_point_overrides`)
The Review page's **Upcoming** section lists **uncompleted** Todoist tasks that have a **due date** (`getActiveDatedTasks()`): content, a "Due <date>" pill (Todoist's natural-language `due.string`, else the raw date read as a LOCAL date so it doesn't shift a day), a points input, **Save**, and **Clear** when a value is set. No label chips. Saved values re-display on reload because `GET /api/upcoming` left-joins the live task list with saved overrides; inputs are seeded from them but never clobber one being edited. The section refetches on mount and on `todoist:synced` (skipped while its own reorder is in flight) and drag-reorders as list `'upcoming'`. It keeps its own state and never touches the Completed section's action guard (`beginAction`/`endAction`, `pendingActions`, `actionGen`), so its saves and refetches can't interfere with Completed's assign/discard handling.

`task_point_overrides (task_id TEXT PRIMARY KEY, points INTEGER NOT NULL, content TEXT, created_at)` — keyed by the **ACTIVE Todoist task id**. Save = `PUT /api/upcoming/[id] {points, content?}` → `upsertTaskOverride` (points integer in [1, 100000] via `parseIntInRange`, 400 otherwise; id 1–200 chars; content capped at 2000 chars). Clear = `DELETE /api/upcoming/[id]` (idempotent). **Clearing is a DELETE, never a 0-point save.**

**ID linkage (verified empirically 2026-07-08):** the unified API v1 `/tasks/completed/by_completion_date` returns the full task object, whose `id` **equals** the active task's `id`, so an override keyed on the active id matches a completion directly on `completedTask.id`.

The nav badge (`ReviewNavLink`) counts only the Completed queue.

### Review queue (Completed)
Completions without a pre-set value land in `pending_review` (see "Sync precedence").

`pending_review` schema: `(completion_id TEXT PRIMARY KEY, content TEXT NOT NULL, labels TEXT, completed_at TEXT, created_at TEXT NOT NULL DEFAULT (datetime('now')))` — `labels` (JSON array) is still written for schema stability but never read or displayed.

On the `/review` page, **Assign N** records a normal `earn` ledger row (`source_id` = completion id, description = `"<content> (manual review)"`; the suffix is stripped for display) and removes the queue row; **Discard** just removes the queue row. **Discard all (N)** (in the Completed section's header only, only when the queue is non-empty; it only ever touches `pending_review`, two-step inline confirm) snapshots the completion ids on screen when the confirm is armed and sends them: `POST /api/review/discard-all {ids}` → `discardPendingReviewIds(ids)` deletes ONLY those ids in one transaction and returns `{ ok, discarded }` (the count actually deleted). This is deliberate: auto-sync can queue more items between page load and Confirm, and those must survive (never discard what Graham hasn't seen). `ids` must be a non-empty array of ≤5000 non-empty strings, each ≤200 chars (400 otherwise); the page then reloads and dispatches `todoist:synced` so the nav badge updates. In every case the completion stays in `processed_completions`, so it is never re-queued ("going forward only" — no backfilling of history).

**Assigning 0 = discard.** The award API route (`review/[id]/award`) accepts an integer in **[0, 100000]**. `points === 0` routes to `discardPendingReview` (drop from the queue, no ledger row, balance unchanged) and returns `{ ok, newBalance }`; `points >= 1` awards as normal. `awardPendingReview` keeps its own `>= 1` guard (defense in depth) and runs in a transaction, so 0 can never create a ledger row. Default input value is 1.

### Balance adjustments (set / reset)
`balance_adjustments (id, delta INTEGER NOT NULL, note TEXT, created_at)`. The dashboard Balance card (`src/app/BalanceCard.tsx`, `"use client"`) has an **Adjust** control: a number input prefilled with the current balance + Save/Cancel, and a **Reset to 0** shortcut with a two-step confirm. Both `POST /api/balance {balance}` → `setBalance(target)`, which in one transaction reads the current balance and inserts `delta = target − current` with note `"Balance set to N"` (a zero delta inserts nothing). Input must be an integer in [0, 1000000] (400 otherwise; `parseIntInRange` refuses `null`/`""`/booleans/arrays so they can't coerce to 0 and wipe the balance). Success dispatches `todoist:synced`. The dashboard's **"Spending & adjustments"** list merges redemptions and adjustment rows (signed delta), newest first, so the number stays explainable. Ledger rows are never rewritten by an adjustment.

### Habits
Tables (all additive): `habits (id, name, points, created_at, archived_at, description)`, `habit_checks (habit_id, date, ledger_id, status, PK(habit_id,date))`, `habit_bonus (date PK, ledger_id)`, `app_settings (key PK, value)` holding `habit_bonus_points` (default **10** when unset; 0 = no bonus).

**Column migrations (the prod DB already has these tables).** `CREATE TABLE IF NOT EXISTS` never alters an existing table, so columns added after a table shipped come from `addColumnIfMissing()` at the end of `initSchema()` in `db.ts`: it checks `PRAGMA table_info` and runs `ALTER TABLE … ADD COLUMN` only when the column is missing (idempotent, additive, never a rebuild). The same column is also in the `CREATE` statement, placed LAST so a fresh DB and a migrated one end up with identical schemas. Current migrations: `habits.description TEXT`, `habit_checks.status TEXT NOT NULL DEFAULT 'done'` (existing checks become 'done'). `src/lib/db.test.ts` builds the old-shape tables with rows in a temp DB, runs init twice, and asserts the rows survive and the columns match a fresh DB. Follow this pattern for any future column.

- **Dates are the client's local calendar date** (`YYYY-MM-DD`), sent in the URL. The server runs in UTC and must NOT derive "today" for a check; it only validates the format + real calendar date and bounds it to [server UTC date − 60 days, server UTC date + 1 day] (`isDateInCheckWindow` in `dates.ts`). The `/habits` page computes its 7 days with `lastNLocalDates` on every load (so it rolls over at local midnight), never during render (the page is prerendered).
- **Three states per cell:** not marked (no row), **done** (`status 'done'`, earns points, `ledger_id` set) and **missed** (`status 'missed'`, earns nothing, `ledger_id` NULL). `setHabitStatus(habitId, date, 'done'|'missed'|null)` handles every transition. **Mark** = `PUT /api/habits/[id]/checks/[date]` with optional JSON `{status: "done"|"missed"}`: an absent/empty body or an object without `status` means "done" (backward compatible); any other body is a 400. Becoming done inserts an `earn` ledger row (points = the habit's CURRENT points, description `Habit: <name>`, source_id `habit:<id>:<date>`); done → missed deletes that row by `ledger_id`; missed → done creates one. **Clear** = `DELETE` (either status), deleting any ledger row, tolerating that row already being gone (removed from the dashboard). All idempotent, in one transaction with the bonus recompute for that date, returning `{ ok, status, done, bonus, newBalance }`; unknown or archived habit → 404, bad id/date → 400. A habit CAN be ticked for a date before its `created_at` — deliberately not rejected: `created_at` is UTC, so a habit created on a US Eastern evening has tomorrow's UTC date, and rejecting earlier dates would stop Graham ticking it for that same evening. (Such a tick earns the habit's points but doesn't make the habit required for that day's bonus.)
- **Bonus recompute for D:** eligible = active habits with `date(created_at) <= D`. If there is at least one and every one has status **'done'** for D (a missed or unmarked habit blocks it), ensure a bonus row exists (`earn`, points = the CURRENT `habit_bonus_points`, description `All habits done (<D>)`, source_id `habit-bonus:<D>`; not awarded when the setting is 0); otherwise delete any bonus row for D. The bonus value is captured when awarded — changing the setting (`PUT /api/habits/bonus {points}`, [0, 100000]) never rewrites past rows. Known lenient edge: `created_at` is UTC, so a habit added late on a US evening (already tomorrow in UTC) isn't required for that evening's bonus. Adding or archiving a habit does not recompute any bonus; the next tick on a date does.
- **Remove** = archive (`DELETE /api/habits/[id]` sets `archived_at`): past checks and ledger rows stay; archived habits drop out of the grid, eligibility and toggles.
- Habit and bonus rows are ordinary `earn` ledger rows: they show in Recent earnings (with Edit/Remove), count toward the balance, and never touch `processed_completions` or `pending_review`.
- `GET /api/habits?from&to` (inclusive, at most 14 days) → `{ habits (drag order, list key 'habits'), checks, bonuses: [{date, points|null}], bonusPoints }`. `POST /api/habits {name, points, description?}` and `PATCH /api/habits/[id] {name?, description?, points?}` share `parseHabitInput()` in `validate.ts`: name trimmed 1–100 chars, points integer [1, 100000], description optional text trimmed to ≤500 chars with blank → NULL (`null` clears it on PATCH). PATCH needs at least one field and 404s an unknown/archived habit. **Editing points affects future marks only** — ledger rows already earned keep their value (and their old `Habit: <name>` description).
- **Page (`src/app/habits/page.tsx`):** rows = habits (name, optional description in small slate text that wraps, "+N pts", **Edit** and Remove with two-step confirm, drag grip), columns = the last 7 local days (header "Mon / 23", today in emerald), each cell a 40px button that cycles **blank → done (emerald ✓) → missed (rose ✗) → blank**, with an aria-label like "Read, Mon 23: done / missed / not marked". **Edit** turns the row's title area into an inline form (name, description textarea, points, Save/Cancel; `text-base` inputs on phones) with a hint that new points apply to future ticks only. Marks are optimistic and revert on error. A cell (habit+date) is disabled while its own request is in flight (ref-guarded too, so a fast double-tap can't send PUT and DELETE concurrently and land out of order); other cells stay usable. While any toggle is in flight, sync-driven reloads are held back, and the last one to finish dispatches `todoist:synced` (which reloads the grid's bonus row and the balance elsewhere). A bottom row shows "★ +B" on days the bonus was earned. On phones each row stacks (name above, cells below, right-aligned), so 7 cells fit 390px with no horizontal scroll; every row and the header use the same right padding (`ROW_PX`) so the columns line up. Add-habit form (name, optional description, points default 5) and an inline "All-habits bonus: B pts · Edit" setting.

### CI (`.github/workflows/ci.yml`)

Runs on every pull request (the `pull_request` trigger is deliberately
unfiltered, so a stacked PR based on another branch still gets CI) and on
pushes to `main`. One `test` job:
Node 24 (matching the Dockerfile), `npm ci`, then `npm test` (node:test
over `src/**/*.test.ts`, including the real-DB tests) and `npm run build`. The build step is load-
bearing: `npm test` never type-checks, so a dependency bump that breaks a type
or the Next build would pass tests and still be broken. Since Next.js 16.3 the
build type-checks with the project's own `tsc` over everything `tsconfig.json`
includes — test files too (hence `allowImportingTsExtensions`).
Actions are pinned by commit SHA, not by tag — a tag can be re-pointed at
different code. Dependabot's `github-actions` ecosystem keeps the pins fresh;
refresh one by hand with
`gh api repos/<owner>/<action>/git/ref/tags/<tag> --jq .object.sha`.
Every job carries `timeout-minutes` (a job with no timeout burns a runner for
six hours when it stalls — km-tracker issue #84 was filed for exactly that).

**There is deliberately NO lint step** — there is no ESLint config and no
`lint` script (issue #20; Next.js 16 removed the `next lint` command, which
used to drop into an interactive prompt and hang forever in CI). A lint step
that can stall would, because auto-merge depends on this job, silently stop
every Dependabot PR rather than merging it. Verify with `npm run build` +
`npm test` until #20 lands.

### Dependabot auto-merge — what merges itself, what stops for Graham

`ci.yml` has a `dependabot-auto-merge` job. **Merges itself**, with no review,
only when ALL of these hold:

1. The PR author is `dependabot[bot]`, and `dependabot/fetch-metadata` confirms
   the head commit was authored by Dependabot **and carries a verified
   signature**. Nobody can hand-craft a PR into this path.
2. **Every other job in the same workflow run succeeded** — that is literally
   the `needs:` list, which names every sibling job.
3. The update is **semver-minor**, **semver-patch**, or a **Docker digest
   refresh** (same image tag, rebuilt digest).

**Always stops for Graham:**

- Any **major** version bump — *including a security update*. A security fix
  that crosses a major still waits for him.
- Any PR where no semver level could be derived and it is not a digest refresh.
  An unknown update type is an absence of signal, never a pass.
- Anything whose tests failed, errored, or did not run. **A run with no checks
  can never merge**, because the merge step is unreachable unless the jobs it
  needs actually reported success.

**The gate is `needs:`, not branch protection — do not "simplify" it to
`gh pr merge --auto`.** GitHub's native auto-merge only waits for checks that
branch protection marks as *required*, and none of these repos define required
status checks (baby-pool is private, where the plan offers no branch protection
or rulesets at all). On such a repo `--auto` silently degrades to "merge now",
which would merge a PR whose tests never ran. Depending on the sibling jobs
behaves identically on every repo, protected or not. For the same reason
`allow_auto_merge` is deliberately left **off** — the design does not use it.

The trigger is `pull_request`, **not** `pull_request_target`. The auto-merge
job checks out nothing and runs no PR code; the only job that runs repository
code is `test`, which holds a read-only token. A `pull_request` run from a fork
gets a read-only token regardless of the `permissions:` block, so the write
scopes are unreachable from a fork.

Each run writes its decision and reasoning to the job summary, so the reason a
particular PR did or did not merge is always on the run page.

**Known false negative (safe):** for a bounded requirement range —
`Update X requirement from <4.0,>=3.0 to >=3.1.3,<4.0` — `fetch-metadata`'s
regex reads the bounds as the versions and reports **semver-major**, so these
stop for Graham even though they are minor floor bumps. That is the fail-closed
direction, and it is left alone on purpose: overriding a "major" verdict with
home-grown parsing would turn a safe stop into a possible unsafe merge.

## Deployment / self-hosting

Production runs in **Docker** on Graham's Ubuntu home server (Tailscale SSH `graham@100.101.1.28`, app dir `~/todoist-points`), reachable ONLY at **https://todoist-points.graham-williams.com** through the existing Cloudflare Tunnel + Cloudflare Access (one-time PIN). Full runbook: **`DEPLOY.md`**. Key facts:

- `next.config.mjs` uses `output: "standalone"`; the multi-stage `Dockerfile` (node:24-bookworm-slim, **digest-pinned** on all three FROM lines, non-root `node` user) runs `node server.js` on port 3000 and asserts better-sqlite3's native addon made it into the standalone output.
- **Sign-in: app-level shared-password gate** (`src/proxy.ts` + `src/lib/auth.ts`, the active auth model) — replaces the Cloudflare-Access emailed-PIN login. When **`APP_PASSWORD`** is set the gate is ON: any request that isn't a public path and lacks a valid signed session cookie is **redirected to `/login`** (or **`401`**'d for `/api/*`). `/login` is a plain-HTML password form POSTing to **`/api/login`**, which does a **constant-time compare** (HMAC-SHA256 of input vs `APP_PASSWORD`, both keyed by `SESSION_SECRET`, digest compare — never raw `===`), rate-limits failed attempts (**10 / 15 min per client IP**, in-memory Map keyed off `CF-Connecting-IP`→`x-forwarded-for`), and on success sets a **signed** session cookie (`tp_session` = `v1.<issuedAt>.<HMAC>` signed with **`SESSION_SECRET`**; the raw password is never stored) — **HttpOnly, Secure (in prod), SameSite=Lax, ~30-day** maxAge — attributes come from the single `sessionCookieOptions()` helper in `src/lib/auth.ts` so the set-on-login and clear-on-logout paths can't drift (asserted on the helper in `src/lib/auth.test.ts`, and on the **real `Set-Cookie` header** of `POST /api/login` under `NODE_ENV=production` in `src/app/api/login/route.test.ts`). `/logout` (GET or POST) clears it with the same attributes and `303`s to a **relative** `Location: /login` (asserted for both methods in `src/app/logout/route.test.ts`). The `next` redirect target is **open-redirect-validated** (`safeNextPath`: local single-slash paths only). **Public/exempt paths** (reachable unauthenticated): `/login`, `/logout`, `/api/login`, `/api/logout`, **`/api/health`** (200 liveness probe), `/_next/*`, `/favicon.ico`, `/icon.svg`, `/apple-icon`, `robots/sitemap`. **`APP_PASSWORD` unset/empty ⇒ gate OFF** (app behaves as before) — so it ships dormant and is turned on at cutover. **Shared password by design** (Graham accepted it lets invited friends in); no per-user logic. Everything is **WebCrypto only, zero new npm deps**; unit-tested in `src/lib/auth.test.ts` (`npm test`, Node's native TS type-stripping — no test-runner dep). `src/proxy.ts` is Next.js 16's `proxy` file convention (renamed from `middleware.ts`; the exported function is `proxy`); proxy always runs on the **Node.js runtime** (not Edge), and the `/login` redirect's `Location` is relative (`/login?next=…`).
- **Origin HTTPS enforcement (issue #21, `src/proxy.ts` + `src/lib/https.ts`)** — defence in depth behind Cloudflare's zone-level "Always Use HTTPS", which is one dashboard toggle away from regressing. Two parts: **(1) http→https redirect.** A request is redirected only when **all three** of these hold — it carries a **Cloudflare marker** (`CF-Connecting-IP`, or a parseable `CF-Visitor`), the **visitor's scheme is plainly `http`** (`CF-Visitor`'s `scheme` wins when present, else `X-Forwarded-Proto`), and the request's **`Host` equals `APP_HOST`**. The response is a **`307`** to `https://<APP_HOST><path><query>` with **`Cache-Control: no-store`** and **`Vary: X-Forwarded-Proto`**. **(2) HSTS.** Every response *that reaches the middleware* carries **`Strict-Transport-Security: max-age=31536000`** — deliberately no `includeSubDomains`, no `preload` (each sibling host owns its own policy; matches the apex landing page). Five load-bearing rules, in order of how easy they are to break:
  - **Build the target from `APP_HOST`, NEVER from `req.url`, `Host`, or `X-Forwarded-Host`.** Inside the standalone server `req.url`'s host is the container bind address (`0.0.0.0:3000`) → `Location: http://0.0.0.0/` → `ERR_CONNECTION_REFUSED` (the PR #13 bug, already shipped once). Reflecting a client-supplied host would be an open redirect; verified live that `X-Forwarded-Host: evil.example` is ignored. `Host` is a **guard only**, never copied into the target. The same bind-host trap applies to every redirect: route handlers that send the browser to a local path (`/api/login`, `/logout`) set a **relative** `Location` themselves (no host at all), because a route handler emits whatever URL it is given. The proxy's `/login` gate is the one exception that may use `new URL("/login", req.url)`: Next's middleware adapter strips the host from a same-origin redirect, so the header still goes out relative (measured: `307 location: /login?next=…`). Only this cross-scheme redirect needs an absolute URL, and that one comes from `APP_HOST`.
  - **⚠️ THE GOTCHA: Next SYNTHESIZES `x-forwarded-proto: http` (and `x-forwarded-host`) when the client didn't send them.** Measured against the built standalone server — `npm test`'s hand-built `NextRequest` does **not** reproduce it, which is exactly how the first pass of this feature shipped a latent bug. Two consequences, both permanent traps: *(a)* "no forwarded proto header" does not exist by the time middleware runs, so any `isForwardedPlainHttp(null)` branch is dead code; *(b)* a proto-only rule really means "redirect everything **unless** something says https", which redirects a request that never went through Cloudflare **to the URL it already asked for** — an infinite loop, and with a `301` a *permanently cached* one. **The `CF-*` marker requirement is what makes the code fail OPEN there** (same posture as the four sibling Flask apps), and the **`307`+`no-store`** is what stops any future mistake outliving its own fix. Don't "simplify" either away. The `Host` guard is a second, independent reason the deploy probe (`docker compose exec … fetch('http://localhost:3000/api/health')`, which asserts **200**) is never redirected. There are **no per-path exemptions**; don't add any. **Verifying the redirect by hand needs `node:http` with `setHost: false`, NOT `fetch` — undici silently rewrites the `Host` header to the URL's authority, so a `fetch` probe arrives as `Host: localhost:3000`, is correctly *not* redirected, and prints the `/login` gate — a false negative that reads as a broken feature. Recipe + expected output in `DEPLOY.md`.**
  - **Unset/empty/malformed `APP_HOST` ⇒ no redirect (fail open)** so local dev, `npm test` and CI keep working; a malformed value (scheme, slash, userinfo, whitespace) is refused rather than emitted. **`SAFE_HOST_RE` also requires at least one DOT in the host part and refuses an all-digits final label** (B1, from the 2026-09-19 break-staging sweep) — a public origin pin always has a dot, and without those two guards `APP_HOST=localhost` (or a bare IPv4 literal, or the compose service name `todoist-points`) *validated*, so every plain-http visitor got a live `Location: https://localhost/…`: broken for everyone, and silent precisely BECAUSE the value passed, so the fail-open branch never fired. **The optional `:port` still works and is this repo's deliberate difference from the four Flask siblings** (their `APP_HOST` is a bare hostname) — but the host part itself now needs a dot, so it is spelled `staging.example.test:3000`, never `localhost:3000`. Strictly a tightening: `todoist-points.graham-williams.com` (± `:443`), the apex and `a.b` all still pass.
  - **`Vary: X-Forwarded-Proto` is on EVERY response, not just the 307** (B2, same sweep) — the 200s/302s the redirect gates are equally scheme-dependent, so a shared cache could otherwise store an https-served 200 and later hand it to a plain-http request. Applied in the same middleware wrapper as HSTS via **`addVary()` (`src/lib/https.ts`), never `headers.set("Vary", …)`** — assignment would clobber a `Vary: Cookie` the session layer adds. `addVary` is idempotent and case-insensitive (so the 307, which already carries the header, is not doubled) and leaves a `Vary: *` alone.
  - **The https check runs FIRST**, before the origin pin and the password gate, so a plain-http visitor is bounced instead of being served the login form in the clear. HSTS is attached in a single wrapper around the whole proxy, so it also reaches the short-circuit responses (`/login` 307, `/api/*` 401, origin-pin 403) — a `next.config.mjs` `headers()` entry would **not** cover those, since a response returned from the proxy never reaches the routing layer that applies them.
  - **"HSTS on every response" is not literally true, and can't be made true from here.** Next's own routing layer answers some malformed requests *before* the proxy runs — e.g. an absolute-form request line (`GET http://evil.example/x HTTP/1.1`) gets a framework `308` with `Location: http:/evil.example/x` and **no HSTS, no `no-store`**. Pre-existing on `main`, not something this code can intercept (see the open issue). Exploitability is ≈0 (no browser sends absolute-form; Cloudflare normalizes it), but don't claim blanket coverage in a security review.
  - Tests: `src/lib/https.test.ts` (pure helpers, incl. the fail-open-with-no-Cloudflare-marker case, the B1 accepted/rejected host corpus and the `addVary` append/idempotence/`*` cases) + `src/proxy.test.ts` (the real proxy: ordering, 307/`no-store`/`Vary`, and HSTS **and `Vary`** on all five middleware response paths). One caveat: Next re-serializes `%20` as `+` in the **query** before middleware sees it, so the live `Location` can differ there from the request; the **path** is untouched.
- **In-app Cloudflare Access JWT verification + origin pin** (`src/proxy.ts`, legacy defense-in-depth, still present but **skipped when the password gate is on**): when `CF_ACCESS_AUD` **and** `CF_ACCESS_TEAM_DOMAIN` are both set (and `APP_PASSWORD` is *not*), every request must carry a valid Access JWT (`Cf-Access-Jwt-Assertion` header, `CF_Authorization` cookie fallback) — RS256 verified via WebCrypto against the team JWKS (fetched from `https://<team>/cdn-cgi/access/certs`, cached in-module for 1h, refetched on kid miss), plus `aud`/`iss`/`exp`/`nbf` checks; failures get a 403. The **`APP_HOST` origin/CSRF pin** runs first for every request (incl. the login POST): non-GET/HEAD with a mismatched `Origin` (when present) or `Host` get a 403. With all these env vars unset (local dev) the proxy is a no-op. **Health signal changed:** the old "403 is healthy" no longer holds once the password gate is on (unauth `/` now **307-redirects** to `/login`) — use the dedicated **`/api/health` → 200** probe instead (see DEPLOY.md).
- **`DB_PATH` env var** (added for this) points the SQLite file anywhere; default stays `./data/todoist-points.db` for local dev. Compose sets `DB_PATH=/data/todoist-points.db` with `./data` bind-mounted at `/data`.
- `docker-compose.yml`: single service **named `todoist-points`** — that name is the DNS alias the tunnel ingress targets (`http://todoist-points:3000`), don't rename it. It joins the **external** network `km-tracker_default` (created by the km-tracker compose project, where the cloudflared connector lives). `TODOIST_API_TOKEN`, `APP_PASSWORD`, `SESSION_SECRET`, and (legacy) `CF_ACCESS_AUD` come from a box-local gitignored `.env` (`chmod 600`); compose passes `APP_PASSWORD`/`SESSION_SECRET`/`CF_ACCESS_AUD` through as **optional** (`:-`, empty-safe) and hardcodes `CF_ACCESS_TEAM_DOMAIN=blue-dream-0427.cloudflareaccess.com` and `APP_HOST=todoist-points.graham-williams.com`. **Cutover to the password gate:** set `APP_PASSWORD` + `SESSION_SECRET` (`openssl rand -hex 32`) in the box `.env`, clear `CF_ACCESS_AUD`, redeploy — then remove the Cloudflare Access app.
- **Never add `ports:`** — a published host port would expose the app on the LAN and bypass Cloudflare Access at the edge (the in-app JWT check is a backstop, not a substitute).
- Tunnel ingress + Access app live in the Cloudflare API (remotely-managed tunnel), not on the box.
- Redeploy: `git pull && docker compose up -d --build` from `main`.

### Off-box backups (issue #6, mirrors km-tracker)

The points ledger DB is the **source of truth** (spends/rewards/review decisions/habits/adjustments aren't re-derivable from Todoist), so it's backed up off-box. `scripts/backup.sh` runs on the **host** (not the container) via a systemd timer:

- Consistent snapshot via SQLite's **online backup API** (`python3` stdlib, WAL-safe — never a raw `cp` of the live DB), with a `PRAGMA integrity_check` on each snapshot.
- **Local tier:** deduped-by-sha256 snapshots in `data/backups/` (`todoist-points_<UTC>.db`), pruned to the newest `LOCAL_RETENTION` (default 100).
- **Off-box tier:** `rclone copy` to Google Drive (`gdrive:Hopper/todoist-points-backups`, reusing the box's existing `gdrive` remote that km-tracker set up) — throttled to every `DRIVE_PUSH_INTERVAL_MIN` min (default 15) and only when the DB changed; recent ring buffer pruned to `DRIVE_RETENTION` (default 50), plus a `daily/` long-tail tier (one snapshot/UTC-day, `DAILY_RETENTION` default 30).
- **Fail-safe:** local snapshot always runs; if rclone isn't configured yet it warns and **exits 0** (won't flap the systemd unit), non-zero only when a configured remote actually errors. Never overwrites a good backup with an empty one.
- Config: `.env.backup` (gitignored; copy from committed `.env.backup.example` — **no secrets**, the rclone OAuth token lives only in `~/.config/rclone/rclone.conf`). Units: `deploy/todoist-points-backup.{service,timer}` (installed manually on the box, run as `<user>`, assume repo at `/home/<user>/todoist-points` — set `User=`/`ExecStart` before installing). Full install/verify/restore steps in **`DEPLOY.md` → Automated backups**.

## Security gate

Before **any** `git push`, a parallel panel of skeptical security subagents must run and come back clean. The panel covers, at minimum:
- **Secrets / PII** — no tokens, credentials, `.env`, DB files, or personal task/label data in committed source.
- **Injection / auth / vuln** — SQL injection, unsafe input handling, missing auth/authorization, unsafe deserialization, etc.
- **Dependency / supply-chain** — risky or compromised packages, lockfile integrity, suspicious transitive deps.
- **Data exposure** — endpoints or logs leaking data that shouldn't be exposed.

Each panelist reviews adversarially and must report clean before push is allowed. **Re-run the full panel on every change** — a prior clean result does not carry over to new commits.
